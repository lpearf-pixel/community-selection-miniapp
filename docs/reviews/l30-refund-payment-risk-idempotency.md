# L30 退款/支付风控与幂等设计

## 本阶段目标

L30 在已有人工退款、退款台账 API、Admin 退款台账页面基础上，补齐真实支付/退款上线前需要的前置风控能力：风险汇总、风险明细、CSV 导出、人工退款安全校验，以及重复流水和超额退款识别。

## 为什么 L30 仍然不接真实微信支付/退款

本阶段只处理上线前的可观测性、状态边界和幂等保护，不产生真实资金出入。这样可以先把订单状态、退款状态、金额累计、流水重复与审计视图稳定下来，再进入后续支付/退款 API contract 阶段。

## 幂等保护设计

- 人工退款校验函数统一检查订单是否存在、支付状态是否为 paid、退款金额是否大于 0、单次退款金额是否不超过支付金额。
- 使用订单已记录退款金额加本次退款金额得到累计退款金额，累计值不得超过支付金额。
- 已全额退款或订单状态已进入 refunded 时阻断重复退款。
- 重复 `refund_transaction_id` 与重复 `out_refund_no` 会进入阻断原因。
- 已关闭或未支付订单不允许作为人工退款对象。

## 风险识别规则

- 高风险：单笔退款金额大于支付金额、累计退款记录金额大于支付金额、重复 `refund_transaction_id`、重复 `out_refund_no`。
- 中风险：支付状态为 paid 但 paid_at 缺失、退款状态为 success 但退款金额为 0、退款流水合计与订单退款金额不一致、非 paid 订单存在退款状态、支付状态和订单状态组合异常。
- 低风险：失败团购下 paid 订单仍待人工退款处理。

## 人工退款安全校验

`validateManualRefundSafety` 返回 `ok`、`risk_level`、`warnings`、`blocking_reasons`。它只提供操作前置判断，不执行退款、不修复数据、不变更订单。

## 风险等级说明

- high：需要暂停人工处理并复核支付/退款凭证。
- medium：需要核对状态边界或台账一致性。
- low：属于待人工处理提示，不代表系统已自动处理。

## Admin API 清单

- `GET /api/admin/finance/refund-risk/overview`：退款/支付风险汇总。
- `GET /api/admin/finance/refund-risk/items`：风险明细列表，支持风险等级、订单号、团购 ID、时间范围筛选。
- `GET /api/admin/finance/refund-risk/export.csv`：按当前筛选条件导出风险明细 CSV。

## 风险 CSV 导出安全

CSV 单元格会做两层处理：

1. 以 `=`、`+`、`-`、`@`、制表符或回车开头的内容前置单引号，避免公式注入。
2. 包含引号、逗号或换行的内容按 CSV 规则加引号并转义内部引号。

## 手机号脱敏

Admin 风险响应只返回 `receiver_phone_masked`。完整手机号仅在服务内部读取后立即脱敏，不进入 API 响应或 CSV 输出。

## 数据库变化

- 无新增表。
- 无新增字段。
- 复用 Order、Refund、GroupBuy 与 Refund.raw_notify 中的既有信息进行风险计算。

## 操作边界

- 不自动退款。
- 不自动打款。
- 不自动报税。
- 不新增奖励结算。
- 不在 L30 发起真实微信支付或退款调用。
