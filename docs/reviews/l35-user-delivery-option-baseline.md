# L35 用户自提 / 配送选择基础

## 本阶段目标

在 L33 配送预留与 L34 数据范围基础上，用户下单时可选择“到店自提”或“门店配送”。本阶段只做门店自身履约的信息采集与展示。

## 履约方式

- 到店自提：需要选择自提点，订单详情展示自提点名称、地址、电话和自提码。
- 门店配送：需要填写收货人、手机号、收货地址，并保留自提点作为发货点。

## 为什么先做门店配送

第一版优先服务已有门店和微信群下单场景，门店配送可以先验证真实商品成交、备货、发货点、用户地址展示等基础链路；外部配送接口只保留页面和服务层的 mock / reserved 能力，不创建真实配送单。

## 为什么不做开放配送平台

当前系统定位是社区甄选小程序，不承接外部配送业务，也不做复杂调度、配送员系统、地图 SDK、路线规划或定位轨迹保存，避免超出第一阶段范围。

## 小程序订单确认页变化

订单确认页新增“到店自提 / 门店配送”切换。到店自提展示自提点选择和地址复制入口；门店配送展示收货人、手机号、收货地址输入，以及“当前为门店配送，暂不接第三方配送。”说明。

## 用户订单详情变化

用户订单详情展示履约方式。到店自提订单展示自提点地址和自提码；门店配送订单展示配送地址和根据订单状态映射的配送状态。

## Admin 配送页变化

Admin 配送预留页面默认筛选门店配送订单，展示订单号、收货人、receiver_phone_masked、receiver_address_masked、发货点、delivery_status 和 provider。达达配送接口保持预留说明，不创建真实配送单。

## 后端安全字段边界

后端订单响应继续使用 safe mapper，只返回 receiver_phone_masked，不返回完整手机号，不返回内部成本、服务奖励配置或库存扣减字段。

## L34 数据范围继续生效

后台配送列表和详情继续通过 L34 data scope 过滤，普通店员和门店管理员不会默认全量查看，super_admin 可以全量查看。

## 数据库变化

不新增表，不新增字段，复用现有 Order 字段：pickup_type、receiver_address、receiver_name、receiver_phone、pickup_store_id。

## 后续 L36 建议

L36 可继续补充配送费规则、配送时段、配送范围、门店可配送配置和更完整的配送履约状态流转。
