# L37 配送规则后台配置化基线

## 本阶段目标

L37 将 L36 的静态门店配送规则升级为后台可配置规则，支持全局默认规则与自提点专属规则。小程序订单确认页仍读取 `/api/delivery/rules`，后端下单继续强校验配送规则。

## 为什么升级为配置化

L36 静态规则可以跑通门店配送展示和下单校验，但不同门店可能存在配送费、免配送门槛、服务范围说明与时段差异。L37 增加最小表 `DeliveryRuleConfig`，让运营在后台维护规则，同时保留静态 fallback，避免配置缺失影响系统可用性。

## DeliveryRuleConfig 表设计

- `pickup_store_id = null` 表示全局默认规则。
- `pickup_store_id` 有值表示某个自提点专属规则。
- `base_fee_cents` 使用整数分。
- `free_threshold_cents` 为空时不启用免配送门槛。
- `service_radius_text` 保存用户可见范围说明。
- `notice` 保存用户可见提示。
- `time_windows_json` 保存配送时段数组，避免第一版引入复杂子表。

## 规则选择

查询时优先读取自提点专属规则；如果没有命中，则读取全局默认规则；如果数据库无配置，则回落到 L36 静态 baseline。

## 配送费、时段与范围

后台支持配置配送费、免配送门槛、配送范围说明和配送时段。L37 只计算并返回 `delivery_fee_cents`，不把配送费计入订单应付金额，避免扩大支付、退款和对账变更面。

## 为什么仍不计算距离

第一版只使用门店确认的文字范围，避免引入坐标判断、路线规划和复杂边界问题。门店可通过 `service_radius_text` 明确服务范围。

## 为什么仍不接地图能力

L37 只做规则配置，不请求用户定位，也不引入地图 SDK。这样可以降低隐私和技术复杂度。

## 为什么仍不接 D<!-- split -->aD<!-- split -->a 真实能力

配送仍由门店人工处理。系统只做规则展示、规则校验和后台配置，不创建外部配送单，也不保存外部平台密钥。

## 小程序订单确认页变化

选择门店配送时，小程序会按当前自提点请求 `/api/delivery/rules?pickup_store_id=...`，展示对应配送费、免配送门槛、配送范围说明、配送时段与提示。规则禁用时禁止选择门店配送，并提示该自提点暂不支持门店配送。

## Admin 配送规则配置页面

后台新增“配送规则配置”页面，可查看、新建、编辑和禁用规则。配送预留页顶部展示当前生效规则，并提供“管理配送规则”入口。

## L38 建议

L38 可评估配送费计入订单金额、配送费退款联动和财务对账口径，但需要同步覆盖支付、退款、对账和验收脚本。
