# L53-D2 商品合规与生产发布门禁设计

## 状态

- 日期：2026-07-29
- 状态：已批准
- 目标分支：`codex/l53-first-launch-closure`
- 生产 Runner：仅 `[self-hosted, community]`
- 首发经营主体：个体工商户、小规模纳税人
- 演进目标：有限公司、一般纳税人

## 目标

在不自动下架现有商品、不引入微服务、Redis、MQ 或第二套商品状态机的前提下，为首发商品建立可追溯、可复核、失败关闭的合规闭环：

> 供应商主体档案 → 品类资质包 → 批次进货证据 → 商品审核快照 → 生产发布证据

D2 只解决首发商品与发布合规，不实现完整电子发票、税务申报、对象存储上传服务或自动下架。

## 首发品类边界

生产允许的稳定品类代码只有：

| 代码 | 品类 | 边界 |
|---|---|---|
| `vegetable` | 蔬菜 | 初级农产品 |
| `fruit` | 水果 | 初级农产品 |
| `egg` | 禽蛋 | 鲜蛋/初级农产品 |
| `grain` | 杂粮 | 未加工或仅作允许的初级处理 |
| `primary_dried_goods` | 初级干货 | 仍属于初级农产品 |

加工、分装、预包装食品、酒类、保健食品、药品、进口冷链及无法归类的商品默认禁售。规则由版本化代码清单判断；规则不存在、版本无法加载或分类代码为空时失败关闭。

现有 `Category` 保留展示名称，新增稳定合规代码。不能用中文名称模糊匹配决定能否上线。

## 供应商主体

现有 `Supplier` 原地升级，不创建重复供应商表。主体类型包括：

- 企业
- 农民专业合作社
- 个体工商户
- 自然人生产者/农户
- 批发市场档口
- 收购商
- 临时来源

临时来源只可暂存。主体身份、联系方式、来源地址或适用证据不完整时，不得用于商品合规审核。

自营采购必须保留真实上游来源，平台经营主体不能代替真实供应商。

### 供应商证据

供应商主体档案保存结构化、可脱敏字段；证件原文不进入数据库和日志。数据库只保存：

- 受控对象引用
- SHA-256 摘要
- 证据类型
- 签发/生效/到期时间
- 审核状态
- 关键内容指纹
- 创建、提交、审核、撤销的管理员及时间
- 非敏感结构化摘要

证据变更不得覆盖已审核记录。替换证据创建新版本，旧版本保留并标记失效。

## 批次进货证据

现有 `ProductBatch` 继续作为入库批次事实。每个参与商品审核的批次至少可关联：

- 真实供应商
- 产地
- 到货时间与数量
- 进货/收购凭证类型
- 付款证据引用与摘要
- 合格证、检测证明或规则允许的替代证明
- 发票/农产品凭证状态
- 证据有效状态

没有身份、来源、批次或付款证据时不能进入通过审核的商品快照。

## 商品合规指纹

商品当前合规指纹使用确定性 canonical JSON 和 SHA-256 生成。指纹字段：

- 商品名称
- 商品描述
- 合规品类代码
- 主供应商
- 产地
- 资质证据版本及摘要
- 批次证据版本及摘要
- 标签
- 主图
- 详情图

以下运营字段不进入指纹：

- 价格
- 库存
- 销量
- 排序
- 普通促销状态

数组先归一化再排序；空字符串归一为 `null`；日期使用 UTC ISO 字符串。指纹算法和输入 schema 带独立版本号。

## 审核状态机

商品审核采用两个显式命令：

1. `submit`：按当前事实生成指纹与不可变快照，状态为 `submitted`。
2. `approve` / `reject`：复核同一快照并记录决定。

同一管理员可以执行两个动作，但禁止单命令自动通过。每个命令必须具备权限、幂等键、审计记录和安全 V1 错误信封。

审核记录状态：

- `submitted`
- `approved`
- `rejected`
- `invalidated`

审核通过只对记录中的指纹、规则版本和证据版本有效。历史记录不可修改或删除。

## 审核失效

以下任一条件使批准不再满足生产门禁：

- 当前商品指纹与批准指纹不一致
- 供应商主体已禁用或关键身份变化
- 引用资质已到期、撤销、替换或关键指纹变化
- 引用批次证据已撤销、缺失或不再有效
- 品类/资质规则版本不再接受该批准
- 当前商品不属于首发允许品类

价格、库存、销量、排序及普通促销变化不导致失效。

实现优先采用动态有效性判断，避免通过后台任务批量篡改历史审核。可记录 `invalidated` 事件，但生产判定不得依赖异步任务是否已经执行。

## 现有商品迁移

- 迁移不修改现有 `Product.status`。
- 迁移不批量生成虚假批准记录。
- 现有在售商品可继续服务当前线上版本。
- 下一次生产发布前，所有在售商品必须具备有效批准。
- 任一在售商品缺少有效批准，发布门禁失败。
- 管理员可以紧急手工下架商品；系统不自动下架。

这实现已批准的 A 方案：阻止新生产发布，线上旧版本继续运行并发出高优先级告警。

## 发布门禁

发布门禁查询所有 `status = active` 商品并生成机器可读 JSON：

- 检查时间
- Git SHA
- 在售商品总数
- 有效批准数量
- 失败商品及稳定原因码
- 品类规则版本
- 资质规则版本
- 指纹算法版本
- 每个商品的当前/批准指纹

稳定失败原因至少包括：

- `CATEGORY_CODE_MISSING`
- `CATEGORY_NOT_ALLOWED`
- `SUPPLIER_MISSING`
- `SUPPLIER_INACTIVE`
- `QUALIFICATION_MISSING`
- `QUALIFICATION_EXPIRED`
- `QUALIFICATION_REVOKED`
- `BATCH_EVIDENCE_MISSING`
- `APPROVAL_MISSING`
- `APPROVAL_FINGERPRINT_MISMATCH`
- `RULE_VERSION_UNSUPPORTED`
- `EVIDENCE_GENERATION_FAILED`

数据库不可用、规则加载失败或证据无法写出时，进程非零退出并阻止发布。

失败时使用现有 `OpsAlertLog` 写入 `critical` 告警，去重键包含规则版本和失败摘要。成功后可以解决同一门禁的开放告警，但不得删除历史告警。

## 隐私与访问审计

- 后台默认只返回脱敏主体信息和证据元数据。
- 原始证据下载使用短期受控链接或后续对象存储适配器，不通过公共静态 URL。
- 查看/下载记录管理员、证据 ID、用途、时间、IP 和 user-agent。
- 日志、发布 JSON、CI artifact 和错误响应不得包含身份证号、证件原文、手机号明文或对象存储签名 URL。
- 文件删除或替换不能改变历史审核快照；物理保留期由后续数据保留策略处理。

## 财务演进接口

D2 不开发完整开票系统，但数据关系必须支持：

- 商品与真实供应商
- 采购批次与供应商
- 采购/收购凭证类型
- 付款证据摘要
- 发票或农产品凭证状态
- 凭证有效期与审核状态

后续经营主体升级采用“经营主体版本＋税务身份版本”。历史订单、销项发票、采购凭证和资金记录始终归属发生交易时的主体版本，禁止迁改历史归属。

## 非目标

- 不实现消费者数电发票申请和红冲
- 不实现农产品收购发票自动开具
- 不实现一般纳税人进项抵扣
- 不接入外部 OCR 或自动审核
- 不自动下架商品
- 不允许管理员跳过生产门禁
- 不扩展首发特殊食品品类

## 验收

1. D1 路由集成测试清理 `WechatShippingIntent` 后全量测试不再因该外键失败。
2. 规则与指纹纯函数具备 RED/GREEN 单元测试。
3. PostgreSQL 迁移从稳定基线升级成功，迁移安全扫描通过。
4. 同一管理员可分两步提交和审核，但不能单步自动通过。
5. 合规字段变化导致门禁失败，价格/库存变化不导致失效。
6. 资质到期/撤销、供应商禁用及批次证据缺失均失败关闭。
7. 现有 active 商品不被迁移脚本下架，但缺少批准会阻止生产发布。
8. 发布 JSON 不含敏感原文，失败会创建去重的 critical 告警。
9. Focused PostgreSQL Gate 只使用 `community` Runner。


## CI 发布证据 Artifact

Task 8 固定生成并上传名为 `l53-d2-compliance-evidence` 的 GitHub Actions Artifact：

- 唯一文件为 `.github/l53-d2-compliance-evidence.json`，保留 7 天。
- 无论门禁成功或失败均尝试上传；证据文件缺失时上传步骤失败，不允许静默跳过。
- JSON 只包含 Git SHA、检查时间、计数、稳定原因码、规则版本、审核 ID 与合规指纹；不得包含对象键、原始 URL、证件原文、明文身份信息或联系方式。
- Artifact 不包含源码快照，且 D2 workflow 仍不运行浏览器、完整生产镜像或 `verify:all`；这些保留给 L53 最终生产收口。
